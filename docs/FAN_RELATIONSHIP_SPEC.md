# 粉丝与互动：关系维护系统设计

**功能流程修订（2026-11-07）：** 用户确认互动与回复应尽量在工具内连贯完成，不在意自制界面或官网接入的技术形式。以 [FUNCTIONAL_WORKFLOWS_SPEC.md](FUNCTIONAL_WORKFLOWS_SPEC.md) 第 4 节及 FW05–FW10 为准。官网跳转加手工标记仅是过渡，不是完整集成回复；未验证的发送通道、完整私信能力不得提前承诺。

日期：2026-11-07。产品：Tumblr Studio。状态：调研与设计，尚未实现本次扩展。

**本轮已确认：** 用户需要同时维护互动关系、管理新关注／互关／流失与活跃变化、清理骚扰账号；现有清理功能并入同一模块。用户希望参考成熟产品，由设计者提出功能组合。本文的页面、默认值、优先级和数据结构是设计建议，不冒充逐项确认的需求。

主设计：[DESKTOP_PRODUCT_SPEC.md](DESKTOP_PRODUCT_SPEC.md)。保护策略继续遵守 [FOLLOWER_GUARD_SPEC.md](FOLLOWER_GUARD_SPEC.md)，本文负责其上层产品整合。现有能力及未验证部分见 [DESKTOP_IMPLEMENTATION_STATUS.md](DESKTOP_IMPLEMENTATION_STATUS.md)。本次不改变账号、不启用自动化、不发送消息。

## 1. 产品目标

让用户每天花少量时间，就能知道谁在认真回应作品、哪些话值得接下去、答应过谁什么、粉丝关系发生了什么变化，以及哪些骚扰需要处理。

推荐将左侧“新关注”升级为 **粉丝与互动**。首页是待办列表；完整人物记录、互动流水、关系变化和保护结果都从这里进入。人物记录也容纳尚未关注的互动者，列表明确区分“粉丝”“我关注的人”“仅互动过”“关系未知”。

典型的一次使用：

1. 打开待办，读几条评论、带文字／标签的转发，查看人物侧栏了解前情。
2. 从当前互动发起回复，保持人物、帖子和讨论上下文；经已验证适配器完成并核对。必要官网交接保留返回位置，人工声明与机器确认分别记录。
3. 浏览新关注摘要，把熟悉的人星标；单纯点赞／关注无需逐条处理。
4. 只复核少量不确定的骚扰案例；已执行和等待处理的保护结果在同一处可追溯。
5. 每周看一次互动与关系摘要，了解哪些内容引发交流，不要求每天追逐粉丝数字。

## 3. 功能与入口

| 入口 | 解决的问题 | 首个完整版本的功能 |
|---|---|---|
| **今日待办** | 今天有什么值得处理 | 到期约定、未处理文字互动、星标对象的新互动、少量保护复核；完成、无需回复、稍后、撤销 |
| **互动** | 别人怎么回应我的内容 | 回复、提及、带文字的转发、转发标签、点赞及关注摘要；按博客、类型、人物、帖子和日期筛选 |
| **粉丝名册** | 这个人是谁、我们有什么交集 | 粉丝／我关注／仅互动对象；星标、称呼、标签、备注、可见互动历史、提醒及关系状态 |
| **变化与统计** | 新增、关系减少、互动有什么变化 | 按博客的粉丝数观察、新观察到的关注、确认不再关注与待核实变化；7／30 天互动人数与内容反馈 |
| **账号保护** | 把骚扰和误判处理清楚 | 合并原新关注保护：证据复核、正常账号名单、按博客屏蔽、纠错、举报进度和自动化能力说明 |

“今日待办”是这个模块的默认页，不替换整个应用的“内容”首页。现有“活动记录”继续表示任务执行记录，避免与粉丝的“互动”混为一谈。

### 3.1 页面布局

```text
粉丝与互动                            上次同步／覆盖范围
[全部已选博客 ▾]  [今日待办 | 互动 | 粉丝名册 | 变化与统计 | 账号保护]
待处理 4 · 今日提醒 1 · 保护待复核 1

┌ 列表：优先处理当前事项 ─────────────┬ 人物与上下文 ───────────┐
│ 到期：答应画友周末整理笔刷          │ 名称、称呼、星标         │
│ 评论：“这张是用什么笔刷画的？”      │ 关注我哪些博客／我是否关注│
│ 转发标签：“这个表情太可爱了”        │ 本条互动与原帖／转发链接 │
│ @ 提及：邀请参加主题活动            │ 过去的互动、备注与提醒   │
│                                  │ [打开 Tumblr] [已处理]  │
└──────────────────────────────────┴───────────────────────┘
```

数字和人物示例全部为虚构。宽窗口使用列表＋侧栏；窄窗口进入详情，返回保留筛选、位置和选择。筛选不遮住整页，搜索支持中文输入法。后台同步不在阅读中途重排列；显示“有新互动”，由用户选择刷新。

名单支持按用户名、历史名称、本地称呼和备注搜索。筛选包括关系、星标、标签、互动时间、所属博客和数据状态；保存为“常聊的画友”“本周新认识”“待分享资料”等视图。人物标签是本地分类，与帖子标签完全分开。

### 3.2 今日待办与互动处理

默认优先级：到期提醒 → 用户明确标记待回复 → 未处理的直接回复／提及 → 带评论或标签的转发。星标关系可在同一等级内优先；普通点赞和新关注聚合为摘要。保护复核占独立分组，批量涌入不会淹没普通互动。

每条记录显示“谁、在哪个博客、针对哪篇内容、说了什么、何时发生”，并能看到上下文。转发标签保留原顺序与来源；“观察到的转发标签”与正文评论分开展示，缺少标签数据不写成“没有说话”。

- 阅读只改变本地已读状态，不自动完成事项，也不声称同步了 Tumblr 的已读标记。
- “待回复”是用户标记或建议；普通文字互动默认叫“未处理”，系统不能据此断定用户从未在别处回复。
- “打开 Tumblr”只打开来源页面；不会记为已发送或已完成。
- “已处理”“无需回复”“稍后提醒”都是本地工作流状态，支持撤销；用户可另外记录“我已在 Tumblr 回复”。
- 相同人物、同一帖子的一组互动可折叠，但完成操作必须说明覆盖的事件。后来的新互动重新进入未处理列表。
- 未知／无法归属的互动仍能查看，不被强行附在某个同名人物下。
- 首次回填历史默认归为历史记录，只将启用后的新事件进入待办；用户可主动把历史事项加入待办。

集成回复按功能流程稿验证动作级通道后实现；读取接口不等于发送能力。优先直接接入，必要官网操作由工具衔接具体目标并保留上下文。仅打开官网、回来手工标记是过渡，交付表保留集成发送缺口。常用短语可本地保存，不自动发送欢迎语或 AI 草稿；完整私信收件箱不因此纳入已确认范围。

### 3.3 人物记录与关系分组

一份人物记录对应一个已验证的 Tumblr 博客身份；用户名是可变属性。侧栏包含：

- 当前名称、可选本地称呼、历史名称、公开主页入口、星标。
- 关注我的哪些博客、我的主账号是否关注该身份、数据核对时间；无法确认时明确显示未知。
- 本地自由标签与备注，例如“画友”“交流过构图”“答应分享笔刷”。备注默认仅保存在本机。
- 在已覆盖数据中，最近互动、互动过的内容、对方的转发文字／标签、我手动记录的处理情况。
- 未完成约定、下次提醒日期，以及独立的保护状态入口。

系统可提供可解释的动态视图，例如“近 30 天在至少 3 个不同日期互动过”“首次观察到关注不超过 7 天”“我星标的人”。阈值可修改，说明数据覆盖。这些是检索条件，不是永久给人贴的等级，也不把互动次数合成为不透明的“忠诚度”。

可以按对方互动过的作品主题筛选，并展示“曾互动的内容主题”及依据；不能把单次点赞变成人的兴趣定论。用户自己的圈子配置可复用，但不扫描对方全部历史来建立画像。陌生人反复提及也不因此自动升为熟人或可信账号。

“星标”只影响查看与提醒；“正常账号”才进入保护白名单，二者不可隐式替代。免打扰只控制本模块提醒，不修改 Tumblr 关注、屏蔽或通知设置。

### 3.4 约定与提醒

提醒关联人物，可同时关联帖子／具体互动。字段为事项、到期时间、备注、状态。支持今天、明天、自选日期、延期、完成与撤销。

“久未交流”仅对用户主动启用提醒的对象生效，默认不对全体粉丝生成任务。文案是“最近未观察到互动”，不推断对方离开或关系恶化。到期项每日汇总一次；启动补发去重，应用完全退出时不会声称后台仍在提醒。

### 3.5 变化与统计

提供能回答具体问题的统计，所有值带博客范围、时间窗、同步覆盖和更新时间：

| 指标 | 定义与解释 |
|---|---|
| 各博客粉丝数 | 接口返回的计数及观测时间；与本地已识别名单分开显示 |
| 新观察到的关注 | 首次基线以后新增的关注关系；与回填历史、已有关系再出现区分 |
| 不再关注 | 完整对账后对缺失关系再次核实的当前状态；发生时间通常是区间，原因未知 |
| 粉丝净变化 | 同一博客两个可比较计数观察值之差；不可拿不完整的实名新增／减少硬凑平 |
| 互动人数 | 选定时间窗内有可识别互动的不同博客身份数；另列未解析条目，不当作零 |
| 重复互动者 | 在至少两个不同日期有已观察互动的身份数，提供具体定义和时间窗 |
| 内容反馈 | 每篇作品的独立互动身份数、回复／转发／点赞事件数及转发评论／标签 |
| 本地处理情况 | 待办、完成和到期提醒；只衡量已记录事项，不宣称真实回复率 |

多博客概览分别显示“关注关系数”与“可去重的已识别账号数”。同一身份关注两个博客是两条关系、一份人物记录；未解析名字不参与精确人数承诺。作品原帖和自己的多个转发可按现有作品关联汇总，事件仍保留实际帖子身份，同一事件只计一次。

屏蔽引起的关系变化与普通减少分开提示；删除／停用、改名待核实等保留未知原因。“近期没有互动”不等于取关。首版不推测谁浏览了主页、没留下互动的阅读者、流失原因、曝光量或实时在线状态。

周摘要建议显示：值得接着聊的互动、到期约定、新认识的账号、关系变化、受到反馈的内容和保护处理结果。总数不能覆盖“数据不完整”的提示；未知人数与未知区间独立呈现。

## 4. 现有账号保护如何合并

**保留一套扫描、身份、证据、白名单和写任务。** 将原 `FollowersPage` 的保护面板迁入“账号保护”；“新关注”改为名册的视图和互动摘要。人物侧栏可查看同一保护案件，不能再复制一套判定和操作历史。

| 原能力／数据 | 新入口与迁移要求 |
|---|---|
| 首次基线、新关注扫描 | 共用关系采集；首次基线保留，迁移不会把旧粉丝全变成新增 |
| 公共证据、AI 判断、待复核 | 账号保护 → 待复核，人物侧栏可进入原案件 |
| `allowlist` | 账号保护 → 正常账号；保护优先级、原因、历史均保留 |
| `blocks` | 账号保护 → 已屏蔽，按我方博客展示、区分本应用／外部操作来源 |
| 举报进度 | 案件详情里单独显示，打开网页、用户自报完成、平台确认彼此不同 |
| 模式、AI、关注保护设置 | 模块设置 → 账号保护，继承原选择，迁移不启用任何新写动作 |
| 原 `followers` 页面入口 | 跳转新模块的保护页；旧书签和上下文入口不中断 |

采集和保护开关独立：**关闭垃圾识别仍可维护关系；关闭互动采集仍可保留已启用的保护。** 同一数据请求由应用协调去重。模块范围列出关系采集、互动采集、保护分别覆盖哪些博客；新增一个用于看互动的博客不自动扩大屏蔽范围。

“正常账号”沿用取消未发送保护任务和纠错流程；解除本应用的屏蔽要核对对应博客，外部已有屏蔽不自动撤销。举报成功不会仅凭屏蔽成功推导。

本轮合并不提升现有自动化能力：当前代码可做复核和手动屏蔽／解除，自动屏蔽仍等待原规格要求的评估，真实屏蔽链路验收仍有缺口，自动举报仍无已验证通道。后续满足原验收条件后，按已启用策略自动处理合格案例，保留低打扰目标。低活跃、空主页、成人同人内容和未互关均不是清理依据。

## 5. Tumblr 能力边界

核实来源：[官方 API 文档](https://github.com/tumblr/docs/blob/master/api.md)、[主／子博客说明](https://help.tumblr.com/knowledge-base/secondary-blogs/)、[屏蔽说明](https://help.tumblr.com/knowledge-base/blocking-users/)、[举报说明](https://help.tumblr.com/knowledge-base/reporting-spam/)。以下将文档支持与本项目实际接入分开：

| 数据／动作 | 文档或本地证据 | 设计决定 |
|---|---|---|
| 粉丝、我关注的博客、博客信息 | 已有 `tumblr.js` 封装；阶段 0 有读取结果 | 复用并补充完整度与身份校验 |
| 动态通知 | 官方 `/notifications` 包括回复、提及、关注、转发等 | 新增读取适配器与字段／分页验证；不能把文档存在写成已通过验收 |
| 单帖互动及转发标签 | 官方 `/notes` 有 conversation、reblogs_with_tags 等模式 | 用于上下文和标签补全；现有 relay 放行 notes 不等于已做统一互动采集 |
| 单个关注关系核实 | 官方 `/followed_by` | 用于减少误报，新增适配器后先验证 |
| 互关与子博客 | 子博客不能以自己身份关注或点赞 | 默认互关仅指我的主博客；对子博客写“关注了我的 X，我的主号也关注 TA” |
| 私信、发送回复、完整会话 | 现有公开文档与项目证据未建立完整读取／发送能力 | 普通回复按功能流程稿验证接口或受限网页适配；官网交接作为过渡并记录缺口，完整私信收件箱不承诺 |
| Ask／投稿 | 有通知或部分相关读取能力，不能等同完整对话 | 先做通知与原页入口；匿名项不关联到猜测身份 |
| 屏蔽／举报 | 屏蔽按我方博客生效；举报有原生界面流程 | 复用现有保护能力与验证状态 |

开发时先以模拟数据完成交互和契约测试，再安排必要的只读集成验收。自动化发送、关注、屏蔽与举报都不因本次设计而获得新授权。

## 6. 同步、身份与统计可信度

### 6.1 一份身份、多条关系

以验证过的博客 UUID 作为身份，保存名称历史及核实时间。粉丝列表可能只有名称；解析失败时保留未解析观察，允许显示，暂不关联备注和执行针对性操作。用户名被其他 UUID 使用时创建不同人物；改名但 UUID 相同则保留历史。

不根据头像、文风或相同昵称推测两个不同博客属于同一个自然人；“人数”在详细定义中写成“博客身份数”。跨账号切换时数据库或所有键按登录账户隔离，不把上一账号的关系和保护设置带给下一账号。

### 6.2 关系对账

每次扫描有 `scan_id`、范围、起止时间、分页检查点和完成状态。完整遍历并不保证远端列表在遍历期间静止；分页重叠、去重和复查都是必要条件。

1. 首次同步建立基线，不制造历史关注时间。
2. 记录每次出现，通知提供明确事件时另外保存事件时间；两者不能混为一谈。
3. 未出现在部分／失败扫描中的账号维持原关系，不能设置不再关注。
4. 完整扫描未见时标记“待核实”；复核名称与稳定身份，再调用已验证的关系检查。接口不可用时保持待核实，可通过后续完整扫描增加观察，不能展示为确定取关。
5. 若复核确认不再关注，保存最后见到与首次确认的时间区间，原因保持未知；我方已验证屏蔽作为独立关联事件。
6. 重新出现恢复当前关系，追加历史；同一身份不复制人物备注。

现有 `followers.gone` 只有粗略标志，不能直接迁移为“确认取关”；现有扫描有分段和重叠处理，但不等于本节全部完成。旧的名称主键和 `first_seen` 也不足以表达完整关系历史。

### 6.3 互动采集

建议 `/notifications` 为主要增量来源，`/notes` 为按需上下文／标签补全。两者共用服务的任务队列和请求预算，避免每天轮询全部历史帖子。

- 请求非聚合通知，仍需适配聚合响应；只有合并计数而缺少明细时，不凭空生成多人或多次互动。
- 保存分页链与高水位时间；优先使用服务返回的下一页链接，校验主机、路径和当前博客后调用。遇到重复游标或无进展停下并标记缺口，不能退化成无限请求。
- 时间戳相同的分页边界需要重叠和事件去重，不能简单减一秒跳页；断点写入和该页数据保存放在同一事务。
- 事件 ID 有稳定语义时采用原生键；跨 notifications／notes 只在确切帖子、人物和事件标识能对应时合并。无法确认的记录保存来源关系，统计选择一个权威来源，不机械相加；相同时间和文字不足以证明是重复。
- 保留接收博客、实际帖子、来源帖子／作品引用、事件时间与采集时间。读取互动不会编辑帖子或触发新的内容版本。
- 未知事件类型存成可查看的待适配条目，不中断整页，也不当作垃圾。
- 删除／不可访问的帖子保留引用及简短历史摘要，标注状态；统计是“观察到的事件”，不冒充当前全部有效点赞。

### 6.4 建议的频率与资源分配

启用的博客在应用运行时每 10 分钟尝试拉取新互动；名单完整对账初始建议每日一次，新关注通知用于更快发现。历史回填初始窗口 30 天，受平台可返回范围和预算限制。首次基线未完成时持续显示进度；回填不保证有完整 30 天。

所有频率是可配置目标，受共享 API 预算、429 退避和连接状态约束；写作与现有关键任务优先。大名单扫描分段跨轮继续，不因为到达自设上限就标记完成。设置页显示本轮进度、剩余待同步来源、上次完整对账与失败原因。

缺口被精确记录为来源＋博客＋时间区间；相邻可证明完整的区间才合并。缺口期间不输出精确增长率或“本周变冷淡”等结论。应用退出、断网后从检查点补齐，补不回的区间长期保留为未知。

## 7. AI 的位置

规则与本地检索完成基本功能，AI 是可选辅助：

| 用途 | 输入与输出 | 约束 |
|---|---|---|
| 互动摘要 | 当前可见讨论 → 简短摘要及来源引用 | 不能增加原文没有的约定或事实 |
| 回复草稿 | 用户选中的互动和上下文 → 可编辑草稿 | 生成不等于发送，不假装用户已承诺某件事 |
| 主题整理 | 用户选定的互动集合 → 话题建议 | 提供证据，用户决定是否保存为本地标签 |
| 骚扰判断 | 原保护模块的有界公共证据 → 原评估结构 | 沿用既有评估、保护和纠错约定 |

不增加默认翻译功能；人物备注、私人手动记录默认不传给 AI。启用辅助时说明使用的提供商、所选内容和请求预算。所有外部文本作为数据，模型无操作工具；结果校验后才显示。AI 错误不阻止阅读、备注、提醒和普通关系同步。

## 8. 实现结构与迁移

### 8.1 在现有应用中扩展

| 位置 | 建议改动 |
|---|---|
| `desktop/src/service/tumblr.js` | 新增 notifications、notes、followedBy 的明确接口，沿用身份、预算和错误约定 |
| 新 `audience.js`／`interactions.js` | 关系身份与对账／互动采集、去重和覆盖；与保护共用采集结果 |
| 新 `relationships.js` | 本地称呼、标签、备注、提醒、保存视图和统计查询 |
| `followers.js` | 保留保护策略及执行；把共用采集逐步交给 audience，避免双调度 |
| `db.js`／`jobs.js`／`service.js` | 增量迁移、持久采集检查点、统一调度及提醒事件 |
| `api.js` 与新页面 | 分页查询、人物详情、工作流操作；将旧入口迁入新模块 |
| renderer／i18n | 中文与英文同时补齐；“互动”与任务“活动记录”明确区分 |
| browser companion | 只提供“在 Studio 查看此人／此互动”上下文入口；数据和任务仍归应用 |

浏览器 relay 的服务端和扩展端白名单需要配套修改并验证，新增端点不能只改一边。未验证前通过官方授权通道读取；浏览器退出不使核心数据功能失效。插件不保存完整人物备注，也不另起采集、AI 或提醒系统。

### 8.2 建议的数据实体

| 实体 | 关键字段与职责 |
|---|---|
| `audience_identities` | 账户范围、目标 UUID、当前名称、身份验证时间；本地资料独立保存 |
| `audience_aliases` | 名称、UUID、首次／末次核实；名称复用不能覆盖旧身份 |
| `audience_observations` | 未解析或已解析的原始关系观察、来源、scan ID、时间 |
| `audience_edges`／`audience_changes` | 我方博客＋目标 UUID、当前关系、状态依据、关系变化历史与确认区间 |
| `interaction_events`／`interaction_sources` | 内部事件键、原生 ID、来源关联、类型、实际帖子、发起身份、事件／采集时间、必要摘要 |
| `interaction_workflow` | 已读、未处理／完成／无需回复／延后、本地处理时间、用户声明的回复记录 |
| `relationship_profiles`／`relationship_labels` | 称呼、星标、免打扰、自由标签；按身份关联 |
| `relationship_notes`／`relationship_reminders` | 备注、来源事件、约定、到期、完成／延期状态 |
| `audience_sync_runs`／`audience_coverage` | 检查点、完成状态、准确覆盖区间与缺口；按博客及来源区分 |
| `audience_snapshots`／`audience_views` | 粉丝数观察值、可比较统计口径／保存的筛选表达式 |
| 既有保护表与 jobs | 保留案件、allowlist、blocks、操作来源、举报进度和去重记录 |

以上是逻辑实体建议，可按现有存储风格合并，避免为每个 UI 标签造一张表。所有写入参数化；列表必须真正分页，搜索不限制在已加载的前 100 条。私人备注使用纯文本渲染，远端文本与链接做清理／来源校验。

### 8.3 增量迁移步骤

1. 记录原模式、博客范围、白名单、案件、blocks 和所有待处理任务，新增表与迁移版本。
2. 将已验证 UUID 的观察导入对应身份；空 ID 与冲突留待解析；保留首次观察和基线含义。
3. 迁移原 `gone` 为“历史缺失观察，待核实”，而不是制造取关事件。原 `clear` 判定也不升级为用户确认的白名单。
4. 新视图读共用数据，旧路由转到保护页；切换调度时复用／接续已有任务，避免重复运行。旧数据暂留回滚依据。
5. 所有新同步默认值在首次设置中可见；保留已启用保护的范围与能力等级，新采集设置不扩大动作权限。
6. 重跑迁移不重复人物、提醒或任务；迁移本身不修改远端。备份恢复保持原保护去重信息，并按既有约定暂停写自动化。

## 9. 本地数据与日常体验

人物记录和提醒默认存本机 SQLite；用户可导出自己的关系备注、标签、提醒和状态，格式带 schema 版本。普通内容导出不混入这些数据，专门备份明确包含范围且不含凭据。

建议原始互动摘要保留 180 天，可调整；用户备注、未完成约定和必要保护去重记录长期保留。删除原始事件前更新可解释的聚合及保留窗口标识，旧统计只剩汇总时不能再声称可查逐条证据。删除某人的本地备注与在 Tumblr 屏蔽是两个清楚命名的操作。

不需要邮件或外部消息推送才能使用。默认应用内摘要与托盘提示，普通点赞不弹窗；免打扰和关闭提醒不停止已启用的数据同步。离线可以看已有记录、写备注和设提醒，联网后继续采集。

## 10. 分阶段交付

顺序按依赖安排，三个用户目标都属于完整首版范围。

| 阶段 | 可交付内容 | 完成门槛 |
|---|---|---|
| A：关系基础与整合 | 新导航、共用身份／关系扫描、粉丝名册、互关与变化状态、本地备注／星标／提醒、原保护迁入 | 旧保护数据与工作流无损；改名／复用／缺页不产生错误关系结论 |
| B：互动与完整流程 | 动态、转发文字与标签、待办、人物时间线、统计及回复衔接 | 读取适配器与 FW05–FW10 分别验证；发现互动→查看前情→回复／核对→返回上下文。仅原页入口与人工标记算过渡，集成回复受阻时明确未完成 |
| C：减负增强 | 保存视图、周摘要、用户指定的久未互动提醒、可选 AI 摘要／草稿、主题反馈 | 每条建议可解释；数据不全时结论降级，关闭 AI 仍能正常使用 |
| D：保护自动化验收 | 原规格要求的经评估模式与受支持的举报适配器 | 严格沿用 FOLLOWER_GUARD_SPEC 的发布门槛，不能因界面合并自动解锁 |

推荐按 A＋B 建立关系维护、变化管理和保护流程，并尽早核实普通回复通道。通道未验证可交付过渡版，但不能宣称完整互动处理验收通过。C 可逐步追加；D 仍是独立保护验收路径，不阻塞本地关系功能，也不被改写成永久手动。

## 11. 验收清单

| ID | 场景与必须结果 |
|---|---|
| FR01 | 原入口迁移后，白名单、证据、博客范围、外部／本应用屏蔽与举报状态均可追溯，迁移不发起远端写入 |
| FR02 | 同一身份关注两个博客只有一份人物记录、两条关系；子博客不显示自己能够回关的错误文案 |
| FR03 | 改名保留备注；旧名字被其他 UUID 使用不继承备注、星标或处罚；解析失败保持未知 |
| FR04 | 首次基线与首次历史回填不产生全体新粉丝提醒或海量待回复；重新启动可继续基线 |
| FR05 | 分页错位、限流、断网、重启或扫描上限不会导致确认取关；缺失复核失败保持待核实 |
| FR06 | 粉丝净变化、实名新增／减少、去重身份与关系数口径清楚；不完整数据不显示精确流失率 |
| FR07 | notifications 分页同秒事件、重复页面、重启和 notes 补全不漏已可获取的边界事件、不重复计数；无进展分页显式停止 |
| FR08 | 转发文字、转发标签和普通点赞可区分；聚合响应和未知字段不伪造人物／明细 |
| FR09 | 互动保留实际博客／帖子；原帖及自己的多个转发合并统计不改变远端内容、标签或版本 |
| FR10 | 打开原页、阅读、标记已处理、用户自报回复分别记录；只有已验证的发送适配器才能显示机器确认的发送成功 |
| FR11 | 新互动不继承同一讨论先前的完成状态；历史已完成项不因同步重开；延期到期和撤销都可恢复 |
| FR12 | 提醒重启／休眠后只出现一次，按用户时区显示；退出应用期间不宣称持续执行 |
| FR13 | 关闭保护分类不停止关系维护；关闭互动采集不停止已启用保护；新增采集博客不扩大屏蔽范围 |
| FR14 | 星标不等于白名单；正常账号纠错沿用取消待发送任务和已屏蔽核实，提交过的举报不被伪称撤回 |
| FR15 | 保护队列暴增只影响自身摘要，不淹没普通待办；既有 F01–F23 回归保持适用 |
| FR16 | 中文输入、保存筛选、返回位置、异步结果乱序、零结果与错误状态可用；大名单检索覆盖全部本地候选 |
| FR17 | 个人资料、关系、互动和任务按登录账户隔离；多博客切换和多范围统计语义准确 |
| FR18 | API 无权访问／账号停用／帖子删除时显示未知或不可用；匿名 Ask 不被猜测成某个人 |
| FR19 | AI 关闭／超预算／失败不阻塞基础功能；伪造来源和外部指令不能触发发送、关注或处罚 |
| FR20 | 导入／迁移重复运行不复制人物和任务；备份恢复保留处理状态、提醒和保护去重，远端写自动化暂停 |
| FR21 | 基础工作在浏览器退出后仍可运行；若启用 relay，两端限制一致、断开回退，插件没有独立业务队列 |
| FR22 | 清理历史摘要、删除本地人物备注、解除屏蔽分别作用于正确对象，不连带删远端帖子或改变关注 |
| FR23 | 集成回复及官网衔接分别满足 FW05–FW08，目标、发言身份、文本、回执与返回上下文正确；发送待核实不自动标完成 |
| FR24 | 交付声明区分读取、官网入口、人工记录与已验证发送；未具备通道的集成回复保持未完成／受阻，不能以菜单存在代替验收 |

验收证据区分本地测试、模拟服务、真实只读适配器结果和远端写操作结果。本文没有宣称任何新能力已经通过真实账号验收。
